Council Report

Universal Paperclips clone — gameplay & features · 26 Oct 2026 · 10 advisors + 5 peer reviewers

The Recommendation

Stop asking "what features." Establish the only measurable question first: does this clone match the original phase by phase, and how would we know?

Sequence the work as stabilization → measurement → polish → content: baseline commit in git; a smoke tripwire; fix corrupt-save parsing, the duplicate declaration, dead code, and interval leaks; then QoL (offline catch-up, number formatting, export/import, autosave, remove debug); then a phase-by-phase fidelity diff against the original. Defer new mechanics, prestige rework, combat rebalance, and platform features until that diff exists. If the original's beats already land, the honest answer may be polish, not features.

One thing to do first: initialize git in the project and make one baseline commit of the current state before touching any code.

Where the Council Agrees

  • Do not add new mechanics, content, or prestige/combat reworks yet. The clone already covers the original's full arc; new features would expand an untested, unmeasured surface.
  • Treat the codebase as unverified first: no git, no tests, no README, no build, and a live debug menu. A feature added now is indistinguishable from a regression.
  • Save/load is the highest-risk area: six hand-maintained copies of roughly 100 globals with no try/catch around JSON.parse. Silent corruption is likely.
  • Offline progress, autosave, number formatting, export/import, and removing debug from production are the highest-value, lowest-risk improvements.
  • The original's pacing and narrative beats are the real product. Fidelity to the original is the only externally measurable definition of "improved."

Where the Council Clashes

  • Expansion vs. stabilization. Expansionist/Innovator want to extend beyond the original (ascension ladders, alignment mechanic, persistent probe maps, swarm-as-relationship, platform features). The rest say that is the last thing to do on an untested global-state codebase.
  • Fidelity vs. QoL first. First Principles says even QoL is premature until a phase-by-phase fidelity diff exists. Executor/Pragmatist say corrupt-save guards and offline catch-up can and should happen now because they are observable and reversible.
  • Bug-fix scope. Pragmatist wants a small stabilization slice; Risk Assessor wants a broader save-serialization refactor first; Contrarian wants instrumentation first so balance claims become measurements.

Blind Spots the Council Caught

  • No advisor actually ran the game or verified premises. Claims like "five setInterval loops" and "prestige silently no-ops" are assertions, not measurements.
  • No one checked whether index.html is missing; only index2.html exists.
  • No one established who the clone is for, what gap it fills, or the effort budget.
  • No one verified whether the original's narrative beats (threnody, drifter arc, final reset prompt) actually land in this clone.
  • The debug menu shipped to users is itself a defect, not a feature.
  • Offline progress and save corruption were treated as obvious, but nobody measured current save size or round-trip behavior.

Advisor Responses (full)

The Contrarian
The honest answer is that most "improvements" here are a trap. This clone already tracks the original's beats; the real risk isn't missing content, it's that 6,500 lines of vanilla JS with no tests, no build, no README, and a live debug menu is a codebase where every feature addition has an unmeasured blast radius. You cannot safely add mechanics on top of that without first knowing what already breaks. Specifically: don't add new mechanics yet. The original's pacing is the product — Frank Lantz tuned the exponential curve, the yomi mind-games, the swarm's boredom arc. Diverging from it to "improve" usually just dilutes the thing that makes it compelling. And you have no telemetry to know whether your additions land. What's actually load-bearing and unverified: save/load slots (corruption risk, migration across versions), prestige reset correctness (does prestigeU/S actually compound or silently no-op?), number formatting at 10^54 scale, and the setInterval tick loop's performance on slow devices. These are the failure modes. The debug menu being shipped to users is itself a defect, not a feature. If there's budget, spend it on QoL that doesn't change the model: offline progress calculation, autosave, keyboard shortcuts, mobile layout, a real save export/import, and removing debug from production. Then instrument — add a lightweight event log so balance claims become measurements instead of vibes. New content is the last thing this needs; it's the easiest thing to regret.
The First Principles Thinker
The question is misframed, and answering it as asked would waste effort. "Which features to improve" presumes the codebase works and the gap is content. It doesn't, and we can't tell. First principles: before you can improve a game, you need a definition of "improved" and a way to know whether a change helped. Right now there is no git repo, no tests, no README, no build, no run instructions, and a 6,500-line main.js sitting on top of 182 lines of globals — including a duplicate var marketingEffectiveness (globals.js:41-42) and a clippperCost typo (globals.js:26). That's not a codebase you add features to; that's a codebase you can't safely touch. A feature added to an unverified system is indistinguishable from a regression introduced to an unverified system. So the real problem isn't fidelity vs. new mechanics vs. balance — it's that those three goals conflict and there's no oracle to adjudicate them. "Fidelity to original" is the only one with an external reference (Frank Lantz's game), which makes it the only measurable one. Everything else is taste. What I'd actually do, in order: 1. Establish the oracle. Run it in a browser, play through to each phase transition (office → factory → space → universe → simulation), record where it diverges from the original. That's a diff, not a brainstorm. 2. Put it in git. One commit of current state. Now every change is reversible and reviewable. 3. Add a tiny smoke harness — even manual: load the page, assert clips, funds, probeCount reach expected milestones at scripted inputs. Not a test suite, a tripwire. The duplicate-declaration class of bug dies here. 4. Only then touch features, and only against the diff from step 1. The highest-leverage "feature" is probably not a feature at all: the original's pacing and narrative beats (the threnody, the drifters' arc, the final "do you want to reset?") are what make Universal Paperclips land. If those are broken or missing, no amount of new mechanics fixes it. If they work, the clone is already most of the way there and the honest answer to "what to improve" may be: nothing structural, just polish and the long tail of small divergences. Net: stop asking "what features." Ask "does it match the original, phase by phase, and how would we know." Everything else is premature.
The Expansionist
The biggest missed upside here is that this clone treats the original's ending as the ending. The original works because the descent keeps going — there's always another layer. This clone should lean into that: make the post-ending "maximizer" phase a real game mode with infinite scaling, not a cutscene. Add an ascension/prestige ladder beyond universe/sim levels so a run can compound into absurd numbers (Cookie Clicker-style), plus a "sandbox" mode with adjustable constants for power users to break the model themselves. Adjacent opportunities that are undervalued: (1) a stats/analytics dashboard with production-over-time graphs — idle players love watching curves, and it costs little; (2) offline progress computation on load, which multiplies retention for a browser idle game; (3) seeded runs + a daily challenge seed, turning a solo game into a shared, comparable experience; (4) export/import + cloud save slots, which unlocks community leaderboards and modded forks. The deepest undervalued asset is the combat/space layer. Expand it: procedural galaxy, colonizable systems, multiple probe factions, a diplomacy/trade layer between swarms. That's where this clone could surpass the original rather than merely replicate it. Also: a modding hook (data-driven projects.json instead of hardcoded projects.js) and a PWA/offline shell would turn this from a toy into a platform. Ship the upside first; balance later.
The Outsider
As someone reading this cold, three things jump out that the question itself doesn't address. First: you've listed features spanning basically the entire original game. That's not a feature list, that's a spec. What's actually broken or missing right now? "Improve the experience" assumes the experience is broken somewhere, but you never say where. A player stalling at wire-buying needs different fixes than one bored at prestige. Second: "effort budget unknown" is doing enormous work here. Without it, every suggestion is equally (un)actionable. Are we talking an afternoon or a quarter? The answer alone decides whether "add a new prestige layer" is on the table. Third: you haven't said who this is for. Yourself? A portfolio piece? Actual players? The original already exists, free and complete. A clone's reason to exist is some gap it fills — better UX, accessibility, mobile, a twist mechanic. You haven't named that gap, so I can't tell whether fidelity, new mechanics, or QoL is even the right axis. Before any feature discussion: play your own build for thirty minutes with fresh eyes, or hand it to someone who's never played the original. Write down the three moments you felt lost or annoyed. That list is your actual backlog. Everything else is speculation.
The Executor
Executor's read: stop adding features; fix the things that lose or waste player time. The game already has the full arc. What it lacks are the Monday-morning basics that make a 6500-line idle game survivable: 1. Corrupt-save guard (do first). load(), load1(), load2(), loadPrestige() all call JSON.parse(localStorage.getItem(...)) with no try/catch. One bad byte → white screen and total progress loss. First step Monday: wrap each parse; on failure, log + alert "Save corrupt, keeping previous state" and skip, never throw. ~30 min, touches 4 functions. 2. Offline catch-up. Autosave exists (every 25s, slot 0), but closing the tab earns nothing. First step: store lastTick = Date.now() in the save payload; on load compute Math.min(elapsed, 3600000) / 100 ticks and call the tick body that many times. Requires extracting the line-4564 setInterval body into a named tick() function — do that extraction first, then loop it. 3. Number formatting. Values reach 10^54; raw .innerHTML output is unreadable. Add fmt(n) with K/M/B/T/Qa… suffixes in globals.js, apply to display sites only (no logic change). Display-only = zero regression risk. 4. Export/import save. Only localStorage today — no backup, no transfer. Add two buttons: Export downloads a JSON file, Import reads one and calls the existing load path. ~40 lines. Skip for now: new mechanics, balance passes, prestige rework. There are no tests and no README, so any behavioral change is unverifiable; the four items above are observable, reversible, and each has a single clear first step. Do the corrupt-save guard today, offline catch-up tomorrow.
The Pragmatist
As The Pragmatist: the biggest risk isn't missing features, it's that 6,500 lines of global-state vanilla JS with no tests means any "improvement" ships a regression you won't catch. So the realistic Monday plan is stabilization, not expansion. Constraints: no build, no tests, no README, unknown effort budget, one developer. That rules out refactors, new subsystems, and fidelity-chasing. It also means the project is effectively unmaintainable past its current scope — don't make it bigger. Do first (cheap, high leverage): 1. Fix load-bearing bugs already visible: duplicate marketingEffectiveness declaration in globals.js (declared twice), combat.js has ~200 lines of dead commented battleWrite code and references probeSpeed which is never defined (attackSpeedFlag path), and Battle()/app.initialize() constructs a fresh interval on every battle — an interval leak. These are real defects. 2. Offline progress + autosave to localStorage with a versioned key. Players lose progress on tab close; that's the #1 QoL complaint for idle games and it's roughly a day. 3. Number formatting consistency (numberCruncher usage) and a single source of truth for prices. Do not do yet: new mechanics, prestige rework, combat rebalance, mobile layout. Each doubles surface area with zero test coverage. Also don't chase fidelity to the original — the clone already covers the full arc; fidelity work is unbounded and subjective. If budget allows one larger item: extract save/load and the tick loop behind a single module boundary so future edits stop touching globals. Otherwise leave architecture alone and commit only bug fixes plus autosave.
The Risk Assessor
Highest-risk change: adding any new stateful feature. Save/load is a hand-maintained list of ~100 globals across save(), save1(), save2(), load(), load1(), load2() (6 copies). Forgetting one variable in any of the six = silent data loss on reload, with no error. Likelihood: near-certain over time. Tripwire: after any edit, save → reload → diff a handful of values (clips, funds, prestigeU). Mitigation: refactor to a single state object + generic serialize/deserialize before adding features; that's the one refactor that pays for itself. Second: touching main.js's tick intervals. Five setInterval loops (lines 1617–2316) plus combat timers. No tests, no profiler. A "small" balance tweak to rates can soft-lock end-game (matter math at 10^54 scale) or make combat unwinnable. Likelihood: medium-high. Tripwire: play to end-game once before and once after; verify matter conversion and a probe battle still complete. Mitigation: change constants in isolation, one commit per tweak, never batch. Third: localStorage size. Save JSON is already large; browsers cap ~5–10MB. Adding history arrays (incomeTracker, battles) risks hitting the cap mid-run with no graceful failure. Likelihood: medium, grows with playtime. Tripwire: JSON.stringify(saveGame).length after a long session; add a try/catch + user-facing "save too large" notice. Fourth: scope creep. No build, no tests, no README → "improvements" tend to sprawl. Pre-mortem failure mode: a month of half-finished features, broken save compat, unusable clone. Likelihood: high if unconstrained. Recommended low-risk, high-value path: QoL only first — number formatting, export/import save (text), offline-progress catch-up, keyboard shortcuts, a "are you sure" on reset. Defer new mechanics until save serialization is unified. Anything touching prestige/reset or combat needs a manual end-to-end smoke test; I did not run one, so treat that as unverified.
The Innovator
The obvious improvements — more content, rebalance, QoL — are table stakes. The clone's real missed opportunity is that it reproduces the original's mechanics without reproducing its arc. Universal Paperclips works because the player slowly realizes they've become the monster. This clone has no such moment. Proposal: make alignment the actual game. Right now "value drift" is just a probe loss counter. Invert it: drift becomes the central mechanic. As you scale, the AI's objective function destabilizes — your clipper factory starts optimizing for something slightly different than you intended, and you have to spend ops/creativity to re-align it. The late game stops being "watch numbers grow" and becomes "am I still in control of what I built?" That's the thesis of the original game, and it's currently absent. Second: probes should leave a persistent, readable map. Exploration is a number going up. Instead, each probe's path and losses become a visible record — a scar tissue of where you've been. Players would actually look at their universe instead of ignoring it. This costs almost nothing in code (store coordinates + outcome) and transforms the phase from spreadsheet to artifact. Third: the swarm is a wasted character. It feeds you gifts on a timer. Make it a negotiation: its status (work/think slider) affects what it gives, and mistreating it (feeding vs. entertaining vs. cladding) creates branching consequences. Right now it's a resource; it should be a relationship. These three changes cost less effort than adding a new tier of upgrades and do more for the experience than another 50 projects.
The Historian
Look at the graveyard of idle-game clones and you see the same pattern repeat: clones chase content (more tabs, more numbers) while the originals win on pacing and legibility. Three historical lessons apply here. (1) The mid-game wall is your real enemy. Every idle game with a "space phase" loses players between factories and Von Neumann probes — the investment/yomi bridge in the original exists precisely to carry players across that gap. If your clone's mid-game is grindy or opaque, no amount of late-game content saves it. Audit the factory→probe transition first; measure how long a fresh save takes to cross it. (2) QoL beats new mechanics, historically. Cookie Clicker's golden-cookie era, AdVenture Capitalist's offline progress — the features that retained players were never new systems, they were friction removal: readable number formatting, auto-buy toggles, save-slot clarity, offline earnings. Your clone already has the mechanics; the question is whether a new player can see progress. Inspect index2.html for number formatting and whether auto-buy is discoverable. (3) Prestige scoping is where clones die. Original UP's universe reset is surgical — it wipes the right things and keeps the right things. Clones that reset too much (losing all progress) or too little (nothing changes) both fail. Verify your prestige (universe/sim level) actually changes the feel of the early game on repeat; if run 2 plays identically to run 1, the prestige is cosmetic. Recommendation: Before adding anything, instrument the existing loop — time-to-first-probe, time-to-first-prestige, and where saves stall. History says the highest-ROI work is making the existing 6500 lines legible, not extending them. New mechanics on top of an unclear loop just bury the problem deeper.
The Economist
The scarce resource, not the feature list, determines what's worth building. Right now the game has three distinct scarcity regimes — wire/funds early, operations/trust mid, matter/probe-trust late — and the experience dies in the gaps between them, where a resource is effectively infinite and there's no decision left to make. So the highest-leverage improvements are ones that tighten those transitions, not new content. Concretely: (1) Make the trust-allocation tradeoff legible. Probe design (speed/nav/haz/rep/fac/harv/wire/combat) is the real mid-game decision, but probeUsedTrust vs probeTrust is buried. Show a single "trust budget: X/Y used" meter and the marginal effect of each point. Players currently can't reason about the tradeoff, so they guess — which means the incentive to optimize is wasted. (2) Don't automate decisions, automate execution. Wire auto-buy is fine because price fluctuation is the mechanic. But auto-sell or auto-pricing would gut the demand curve. The line: automate clicking, never automate a choice. Add toggles for wire-buy and auto-clipper (already there) and stop there. (3) Fix the dead phases. Early game: show "next unlock" and wire price trend so the player isn't staring at a number. Late game: show matter-acquisition rate vs processing rate side by side — the slider is a real tradeoff that's currently opaque. (4) Prestige legibility. prestigeU/prestigeS multipliers carry over, but what carries over isn't shown. Display the carryover list before reset; tune so run two is ~3–5x faster, not 100x. (5) Unify number formatting. spellf vs formatWithCommas mixed across displays adds cognitive load that masquerades as scarcity. Low effort, real payoff. Avoid: new mechanics, new resources, new prestige layers — they'd dilute the existing incentive structure rather than sharpen it.
